Level 1 · Topic 01

The Problem: Recursion Repeats Work 💥

You can't love the cure until you've seen the disease. Watch plain recursion solve the same subproblem again and again — then you'll know exactly why DP exists.

🌍 Start From Zero — What Is Recursion?

Real-Life Analogy

You're standing in a queue and want to know your position. You ask the person ahead: "what's your position?" They ask the person ahead of them… until the front person says "I'm 1st!" The answers flow back: 1 → 2 → 3 → you're 4th. A function asking a smaller version of itself — that's recursion.

The classic example: Fibonacci numbers — each number is the sum of the previous two: 0, 1, 1, 2, 3, 5, 8, 13, 21…

FibNaive.java 
int fib(int n) {    if (n <= 1) return n;              // base case — the stopper    return fib(n-1) + fib(n-2);       // TWO more calls… each!}

🎯 The Two Magic Words

A problem is a DP problem when the call tree above has both properties:

  • Overlapping subproblems — the same smaller question appears many times (you saw f(2) three times, f(1) five times).
  • Optimal substructure — the answer to the big question is built only from answers to smaller ones (f(5) = f(4) + f(3), nothing else needed).
💡
DP in one sentence: recursion + never answering the same question twice. The next two topics show the two ways to add that memory: memoization (top-down) and tabulation (bottom-up).

🧠 Quick Check

In the fib(5) tree you just watched, f(2) was computed 3 times. In fib(6), how many times would f(2) be computed?
5 times. fib(6) = fib(5) + fib(4). fib(5) already computes f(2) three times, fib(4) computes it twice → 3 + 2 = 5. The waste itself follows the Fibonacci pattern — that's why the total explodes as O(2ⁿ).
Which pair of properties makes a problem solvable by DP?
Overlapping subproblems + optimal substructure. No overlap → plain divide & conquer (like merge sort) is enough, caching buys nothing. No optimal substructure → small answers can't be combined into big ones, so no table can help.
Level 1 · Topic 02

Memoization — Top-Down DP 📝

Same recursion, plus a notebook. Before computing anything, check the notebook. After computing, write it down. That one habit turns O(2ⁿ) into O(n).

🌍 The Idea

Real-Life Analogy

Your friend's phone number: the first time, you ask them and save it in Contacts. Every time after that, you just open Contacts — you never ask again. Memoization = Contacts for function results. "Memo" comes from memorandum — a note.

Only two lines change from the naive version — the check and the save:

FibMemo.java 
long[] memo;   // filled with -1 at startlong fib(int n) {    if (n <= 1) return n;    if (memo[n] != -1) return memo[n];   // 📖 CHECK the notebook    long ans = fib(n-1) + fib(n-2);    memo[n] = ans;                        // ✍️ SAVE before returning    return ans;}

Same fib(5) tree as Topic 01. This time watch for ⚡ cyan flashes — cache hits. Their entire subtrees fade out: never executed at all.

Press ▶ — when a call finds its answer already in memo[], it flashes ⚡ cyan and its whole subtree fades — those calls simply never happen.
Naive: O(2ⁿ) time Memoized: O(n) time Extra space: O(n) for memo + recursion stack

⚙️ The Memoization Template (Works For Every Problem)

  1. Write the plain recursion first — don't think about DP at all.
  2. Identify what changes between calls (here: just n) → that's your memo key.
  3. Add the check at the top, the save before every return. Done.
🥇
Why interviewers love memoization: it proves you understand the recursion. In an interview, always say the naive recursion out loud first, then add the memo — that's a complete, correct answer even if you never write the bottom-up version.

🧠 Quick Check

With memoization, fib(50) makes how many real computations (not cache hits)?
About 50. The memo guarantees each distinct subproblem is computed once. There are only 51 distinct subproblems (fib(0)…fib(50)) → O(n). From 40 seconds to microseconds by adding two lines.
What plays the role of the "memo key"?
The changing parameters. fib(n) changes only n → 1-D memo. A grid walker changes (row, col) → 2-D memo. Two-string problems change (i, j) → 2-D memo. The parameters ARE the state — remember this, it's Step 1 of the Recipe in Topic 04.
Level 1 · Topic 03

Tabulation — Bottom-Up DP 📊

Memoization starts from the big question and recurses down. Tabulation flips it: start from the smallest answers and build up — no recursion at all, just a loop and a table.

🌍 The Idea

Real-Life Analogy

You can't build the 5th floor of a building first. You pour the foundation (base cases), build floor 1 on it, floor 2 on floor 1… by the time you reach floor 5, everything below is already solid. Tabulation fills the table in an order where everything you need is already filled.

FibTab.java 
long[] dp = new long[n+1];dp[0] = 0; dp[1] = 1;                // base cases = foundationfor (int i = 2; i <= n; i++)    dp[i] = dp[i-1] + dp[i-2];     // everything needed is already filledreturn dp[n];

🔬 Fill the Table Yourself — Pick Any n

🔬 Tabulation Lab — dp[i] = dp[i−1] + dp[i−2]
Choose n (2–12) and press ▶. The two amber cells are being read; their sum lands in the next cell. Notice: we never look right, never look back — pure forward motion.

🪶 Space Optimization — Throw Away the Table

Look at the transition: dp[i] = dp[i-1] + dp[i-2]. Each step only reads the last two cells — so why store all n? Keep just two variables and slide them along:

FibO1Space.java 
long prev2 = 0, prev1 = 1;          // dp[i-2], dp[i-1]
for (int i = 2; i <= n; i++) {
    long cur = prev1 + prev2;       // dp[i]
    prev2 = prev1;                  // slide the window →
    prev1 = cur;
}
return prev1;                       // O(n) time, O(1) space!

⚖️ Memoization vs Tabulation — Which One When?

Memoization (top-down)Tabulation (bottom-up)
StyleRecursion + cacheLoops + array
OrderBig → small (natural thinking)Small → big (must plan the order)
ComputesOnly subproblems actually neededEvery subproblem, needed or not
Stack overflow riskYes, for deep recursion (n > ~10⁵)No recursion → no risk
Space optimizationHard (cache is random-access)Easy (rolling variables/rows)
Best forFirst solve, tricky states, interviews under pressureFinal solution, tight limits, contests
🧭
Practical rule: think top-down (write the recursion, add memo), then if needed convert to bottom-up (base cases become the first cells, the recursive calls become "look left in the table"). Both give the same complexity.

🧠 Quick Check

In tabulation, why must dp[0] and dp[1] be filled before the loop?
Because dp[2] = dp[1] + dp[0]. Bottom-up has one golden law: when you compute a cell, everything it reads must already be final. Base cases are the cells that depend on nothing — the foundation of the building.
Your DP transition is dp[i] = max(dp[i-1], dp[i-2] + val[i]). What's the minimum space needed?
O(1). Only dp[i-1] and dp[i-2] are read → two rolling variables suffice. (This exact transition is House Robber — Topic 06!)
Level 1 · Topic 04

The 4-Step DP Recipe 🧾

Every DP problem — easy or hard, 1-D or 2-D, LeetCode or FAANG interview — is solved by filling the same four blanks. Learn the blanks once, reuse them forever.

🧾 The Recipe

1

STATE — what does dp[i] mean?

One plain-English sentence. dp[i] = ways to reach step i. If you can't say it in words, you don't have a state yet. The changing parameters of your recursion ARE the state.

2

BASE — smallest answers you know for free

The cases needing zero computation: dp[0] = 1, an empty string, capacity 0, amount 0. The foundation of the building.

3

TRANSITION — big from small

Ask: "what was my LAST move?" List every possibility, combine: dp[i] = dp[i-1] + dp[i-2] (sum for counting, min/max for optimizing).

4

ANSWER — where does it sit?

Usually dp[n] — but not always! For LIS it's max(all dp[i]). Decide consciously.

Real-Life Analogy

It's a cooking recipe: ① decide the dish (state) ② gather raw ingredients (base) ③ the cooking rule (transition) ④ which plate to serve on (answer). Change the dish, the recipe structure stays identical.

⚙️ The Recipe In Action — Climbing Stairs

You climb 1 or 2 steps at a time. How many distinct ways to reach step n? Watch each recipe step map to one line:

recipe_applied.pseudo 
# ① dp[i] = number of distinct ways to reach step idp[0] = 1; dp[1] = 1                  # ② basefor i in 2..n: dp[i] = dp[i-1] + dp[i-2]   # ③ transitionreturn dp[n]                          # ④ answer
🔑
The magic question for Step ③: "What was my last move / last choice?" It splits the problem into a handful of cases, each ending in a smaller subproblem. Last stair-move: 1-step or 2-step. Last coin used: one of the coins. Last house: robbed or skipped. Master this one question and transitions write themselves.

📡 How to RECOGNIZE a DP Problem in 10 Seconds

Signal in the problem statementMeaningExample
"count the number of ways…"Counting DP — transitions ADDClimbing Stairs, Unique Paths
"minimum / maximum cost, profit, length…"Optimization DP — transitions take MIN/MAXCoin Change, House Robber
"is it possible to…" (yes/no)Feasibility DP — transitions OR togetherSubset Sum, Word Break
"longest / shortest subsequence, substring…"String/sequence DP — usually 2-DLCS, LIS, Edit Distance
Choices at every step + greedy failsDecision DP (take/skip)Knapsack
n ≤ 1000–5000 in constraintsO(n²) intended — often a 2-D tablemost contest DP
🚫
When DP is the WRONG tool: if subproblems don't overlap (merge sort), if a greedy choice is provably safe (activity selection, coins 1/2/5 ₹ change with canonical denominations), or if you need the actual arrangement of ALL solutions (plain backtracking). DP stores answers, not every path.

🧠 Train Your Recognition — Spot the State

🎯 "A frog jumps 1, 2, or 3 steps. Count the ways to reach step n." — What is the state and transition?
Last move was a 1, 2, or 3-jump → three disjoint groups → add all three. Same recipe as stairs, one extra term. Base: dp[0]=1. You just solved LeetCode 1137-style "Tribonacci" by recipe alone.
🎯 "Given prices of a rod of length 1…n, cut a rod of length n for maximum revenue." — State?
dp[i] = max revenue for length i. Last choice = the length of one cut piece c → remaining rod is a smaller subproblem dp[i−c]. Greedy fails here (a length-10 piece might beat two 5s or vice versa) — that failure is your signal to use DP.
🎯 "Find the maximum element of an array." — DP needed?
No DP needed. Technically dp[i]=max(dp[i−1],a[i]) is a recurrence, but each subproblem is used once — nothing overlaps, nothing is recomputed. A running max does the job. DP is for when caching actually saves work.
Level 2 · Topic 05 · 1-D Counting

Climbing Stairs — Your First Real DP 🪜

LeetCode 70 — the "hello world" of DP and a real interview question at Amazon & Google. One row of cells, the full recipe, zero shortcuts.

📋 The Problem

You climb a staircase of n steps. Each move is +1 or +2 steps. How many distinct ways can you reach the top?

n = 3 → three ways: (1+1+1), (1+2), (2+1). Notice (1+2) and (2+1) count separately — order matters here.

Real-Life Analogy

You're at step 5. How did you get here? Only two possibilities exist: you were at step 4 and hopped +1, or at step 3 and jumped +2. So ways-to-5 = ways-to-4 + ways-to-3. You never need to know the full journey — only the last move.

Recipe blankFilled in
① Statedp[i] = number of distinct ways to reach step i
② Basedp[0] = 1 (stand still — one way), dp[1] = 1
③ Transitionlast move +1 or +2 → dp[i] = dp[i-1] + dp[i-2]
④ Answerdp[n]

🔬 Watch the Ways Grow

🔬 Stairs Lab — ways to reach each step
It's Fibonacci wearing a costume 🎭 — same transition, different meaning. The meaning (Step ①) is what makes it a solution.
ClimbStairs.java 
public int climbStairs(int n) {
    // dp[i] = ways to reach step i
    if (n <= 1) return 1;
    int[] dp = new int[n+1];
    dp[0] = 1; dp[1] = 1;
    for (int i = 2; i <= n; i++)
        dp[i] = dp[i-1] + dp[i-2];
    return dp[n];
}
Time: O(n) Space: O(n) → O(1) with rolling variables

🔀 The Same Skeleton, New Skin — Min Cost Variant

LeetCode 746: each step has a cost[i]; pay when you step on it. Reach the top as cheaply as possible. Only two blanks change: the state becomes a min-cost, and the transition switches from + to Math.min:

MinCostClimb.java 
// dp[i] = cheapest total cost to REACH step i (before paying cost[i])
int[] dp = new int[n+1];
dp[0] = 0; dp[1] = 0;                 // may start at step 0 or 1 free
for (int i = 2; i <= n; i++)
    dp[i] = Math.min(dp[i-1] + cost[i-1],   // came from i-1, paid its cost
                     dp[i-2] + cost[i-2]);  // came from i-2, paid its cost
return dp[n];
🧩
This is how DP mastery actually works: you don't learn 500 problems — you learn ~10 skeletons and practice re-skinning them. Counting → add. Cheapest → min. Best → max. The recipe is the skeleton.

🧠 Quick Check

Why is dp[0] = 1 and not 0? "Zero steps" sounds like zero ways…
One way — the empty way. Sanity-check base cases by testing the first real cell: dp[2] should be 2 (1+1, 2). dp[1]+dp[0] = 1+1 = 2 ✔. If dp[0] were 0 you'd get 1 ✘. Always verify bases against a tiny hand-computed case.
Level 2 · Topic 06 · 1-D Decision

House Robber — Take or Skip 🏠

LeetCode 198. The most important decision pattern in all of DP: at every element, either take it (with a restriction) or skip it — and let max decide.

📋 The Problem

Houses in a row hold money: [2, 7, 9, 3, 1]. Rob any houses you like, but never two adjacent ones (alarm!). Maximize the loot.

Real-Life Analogy

Standing at house i, you have exactly two futures: rob it — pocket its cash but your previous stop can be at most house i−2; or skip it — keep whatever was best up to house i−1. A professional doesn't re-plan the whole street — just compares those two numbers.

Recipe blankFilled in
① Statedp[i] = max loot from houses 0…i
② Basedp[0] = val[0], dp[1] = max(val[0], val[1])
③ Transitionrob i or skip i → dp[i] = max(dp[i-2] + val[i], dp[i-1])
④ Answerdp[n-1]

HouseRobber.java 
public int rob(int[] val) {
    int n = val.length;
    if (n == 1) return val[0];
    // dp[i] = max loot considering houses 0..i
    int[] dp = new int[n];
    dp[0] = val[0];
    dp[1] = Math.max(val[0], val[1]);
    for (int i = 2; i < n; i++)
        dp[i] = Math.max(dp[i-2] + val[i],  // ROB house i
                         dp[i-1]);          // SKIP house i
    return dp[n-1];
}
Time: O(n) Space: O(1) possible (reads only i−1, i−2)
⚠️
Common beginner mistake: thinking "rob alternate houses — 0,2,4 or 1,3". Wrong! For [2, 1, 1, 9] the best is houses 0 and 3 (=11), skipping TWO in the middle. Greedy patterns fail; only comparing both futures at every step is safe. That's why this needs DP.

🔀 Famous Variants — Same Take/Skip Bone

  • House Robber II (LC 213) — houses in a circle: house 0 and house n−1 are adjacent. Trick: run the robber twice — once on houses 0…n−2, once on 1…n−1 — take the max. A circle is just two lines!
  • Delete and Earn (LC 740) — take a number, its neighbors (value±1) vanish. Bucket the values → it literally becomes House Robber on the buckets.
  • Stickler Thief (GFG) — the same problem under an Indian-placement name.

public int rob2(int[] v) {
    int n = v.length;
    if (n == 1) return v[0];
    return Math.max(robLine(v, 0, n-2),   // without last
                    robLine(v, 1, n-1));  // without first
}

Level 2 · Topic 07 · 1-D Optimization

Coin Change — Min Coins 🪙

LeetCode 322 — the most-asked DP question in interviews, and the problem that proves greedy thinking can betray you.

📋 The Problem — and Why Greedy Fails

Coins = [1, 2, 5] (unlimited supply of each). Make amount 11 with the fewest coins.

Your instinct says: "grab the biggest coin first" — 5, 5, 1 → 3 coins. Correct here! But instinct is a trap:

🪤
Greedy failure demo: coins = [1, 3, 4], amount = 6. Greedy: 4 + 1 + 1 = 3 coins. Optimal: 3 + 3 = 2 coins. Grabbing the big coin ruined the future. Whenever a locally-best choice can hurt later, greedy dies and DP takes over.
Recipe blankFilled in
① Statedp[a] = fewest coins to make amount a
② Basedp[0] = 0 — amount zero needs zero coins
③ Transitionlast coin used was some c → dp[a] = 1 + min(dp[a-c]) over all coins c ≤ a
④ Answerdp[amount], or −1 if still ∞ (unreachable)

CoinChange.java 
public int coinChange(int[] coins, int amount) {
    // dp[a] = fewest coins to make amount a
    int[] dp = new int[amount+1];
    Arrays.fill(dp, amount+1);      // "infinity" (safe: can't overflow)
    dp[0] = 0;
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a)
                dp[a] = Math.min(dp[a], 1 + dp[a-c]);
    return dp[amount] > amount ? -1 : dp[amount];
}
Time: O(amount × coins) Space: O(amount)
♾️
Why fill with amount+1, not Integer.MAX_VALUE? Because 1 + Integer.MAX_VALUE overflows to a huge negative number and silently wins every min()! Using amount+1 as infinity is a classic defensive trick — any real answer uses ≤ amount coins, so amount+1 still means "impossible".

🔀 Sister Problem — COUNT the Ways (Coin Change II)

LC 518 asks: how many combinations make the amount? One recipe blank changes (min → sum)… and one subtle thing: loop order.

CoinChange2.java 
// dp[a] = number of COMBINATIONS to make amount a
dp[0] = 1;
for (int c : coins)              // ← coins OUTER loop!
    for (int a = c; a <= amount; a++)
        dp[a] += dp[a-c];
🔄
The famous loop-order rule: coins outside → each coin type considered once in a fixed order → counts combinations (2+5 and 5+2 counted once). Coins inside (like the min-coins code above) → any order → counts permutations (LC 377 Combination Sum IV). For min-coins the order doesn't matter — min(x,x) = x — but for counting it changes the answer completely!

UniquePaths.java 
public int uniquePaths(int m, int n) {
    // dp[r][c] = paths from (0,0) to (r,c)
    int[][] dp = new int[m][n];
    for (int r = 0; r < m; r++) dp[r][0] = 1;   // left edge
    for (int c = 0; c < n; c++) dp[0][c] = 1;   // top edge
    for (int r = 1; r < m; r++)
        for (int c = 1; c < n; c++)
            dp[r][c] = dp[r-1][c] + dp[r][c-1];
    return dp[m-1][n-1];
}
Time: O(m·n) Space: O(m·n) → O(n) keeping one rolling row

Level 3 · Topic 09 · 2-D Decision

0/1 Knapsack — The King of DP 🎒

The most famous DP problem on Earth. Take-or-skip (House Robber) meets a capacity limit — and at least 20 LeetCode problems are secretly this one.

📋 The Problem

A bag holds 4 kg. Items: 💍 (1 kg, ₹15), 💻 (3 kg, ₹50), 📷 (4 kg, ₹60). Each item exists ONCE — take it or leave it (that's the "0/1"). Maximize value.

Real-Life Analogy

Packing for a flight with a strict baggage limit. For every item you hold it up and ask: "worth its weight?" — but you can't answer per-item (greedy fails!). The 📷 alone (₹60) loses to 💍+💻 (₹65). Only trying both futures per item is safe.

Why 2-D now? The state needs two facts: which items I've considered AND how much capacity remains. Two changing values → two dimensions. (Remember the memo-key rule from Topic 02!)

Recipe blankFilled in
① Statedp[i][w] = best value using the first i items with capacity w
② Baserow 0 = 0 (no items → no value), column 0 = 0 (no capacity)
③ Transitionskip item i: dp[i-1][w]  ·  take it (if wt ≤ w): val + dp[i-1][w-wt] → max of both
④ Answerdp[n][W]

Knapsack01.java 
int[][] dp = new int[n+1][W+1];   // row 0 & col 0 stay 0 = base
for (int i = 1; i <= n; i++) {
    for (int w = 0; w <= W; w++) {
        dp[i][w] = dp[i-1][w];                    // SKIP item i
        if (wt[i-1] <= w)                         // fits?
            dp[i][w] = Math.max(dp[i][w],
                val[i-1] + dp[i-1][w - wt[i-1]]); // TAKE item i
    }
}
return dp[n][W];
Time: O(n·W) Space: O(n·W) → O(W) with 1 row
🔁
The 1-D trick and its trap: since each row reads only the row above, one array suffices — but you must loop capacity backwards (for w = W…wt). Loop forward and item i can be "taken twice" — you'd read a cell already updated in this row and silently turn 0/1 knapsack into unbounded coin change! Loop direction is the ONLY difference between the two patterns.

int[][] dp = new int[m+1][n+1];
for (int i = 1; i <= m; i++)
    for (int j = 1; j <= n; j++)
        if (s1.charAt(i-1) == s2.charAt(j-1))

Level 4 · Topic 11 · Sequence DP

Longest Increasing Subsequence 📈

LC 300 — the problem that teaches DP's subtlest lesson: sometimes the answer is not in the last cell, and the state must end exactly at i to work.

📋 The Problem

nums = [10, 9, 2, 5, 3, 7, 101, 18]. Find the length of the longest strictly-increasing subsequence. Answer: 4 → [2, 3, 7, 18] (or [2, 5, 7, 101]).

🧨
The naive state fails! Try "dp[i] = LIS of the first i elements" — you can't write a transition, because knowing the length doesn't tell you what the subsequence ends with, and extending depends on that last value. The fix that unlocks everything: dp[i] = LIS that ends exactly at index i. Now extension is checkable: nums[i] can follow nums[j] iff nums[j] < nums[i].
Recipe blankFilled in
① Statedp[i] = length of the LIS ending exactly at index i
② Baseevery element alone is an LIS of length 1 → all dp[i] start at 1
③ Transitionfor every j < i with nums[j] < nums[i]: dp[i] = max(dp[i], dp[j] + 1)
④ Answermax of the whole array — the LIS may end anywhere!

🔬 Watch Each Element Look Back

🔬 LIS Lab — dp[i] = best chain ending at i
Press ▶ — each element scans everything to its left (cyan = smaller, chainable; faded = too big). It hops onto the longest chain it can legally extend. At the end the winning chain glows green.
LIS.java 
public int lengthOfLIS(int[] nums) {
    int n = nums.length, best = 1;
    int[] dp = new int[n];
    Arrays.fill(dp, 1);                    // ② alone = length 1
    for (int i = 1; i < n; i++) {
        for (int j = 0; j < i; j++)        // look at every earlier end
            if (nums[j] < nums[i])         // legal to extend?
                dp[i] = Math.max(dp[i], dp[j] + 1);
        best = Math.max(best, dp[i]);      // ④ answer can end ANYWHERE
    }
    return best;
}
Time: O(n²) Space: O(n) Pro upgrade: O(n log n) with binary search (patience sorting)
🃏
The O(n log n) idea in one line: keep a list of "smallest possible tail for each chain length"; each new number binary-searches its slot. Learn it after the O(n²) version is automatic — interviews accept O(n²) with the optimization mentioned.

🕵️ The 3 New Ones, in 60 Seconds Each

  • Interval DP: state = a range [l, r]; transition = "try every last-action point k inside the range" → dp[l][r] = best over k of dp[l][k] ⊕ dp[k][r]. Fill by increasing range length. Smell: "merge stones", "burst balloons", "cut the stick".
  • State machine DP: draw the modes as circles (holding stock / free / cooldown), arrows = allowed moves with profits. Then dp[i][mode] = best money on day i in that mode. Smell: rules about what you may do next.
  • Bitmask DP: when "which subset is used" matters and n ≤ ~20, the subset itself becomes the index: mask 10110₂ means elements 1, 2, 4 taken. dp[mask] loops over set bits. Smell: tiny n + "assign all workers/visit all cities".

🧠 Pattern-Spotting Drills — Name That DP

🕵️ "Given a string and a dictionary, can the string be split entirely into dictionary words?" (Word Break, LC 139)
Unbounded feasibility. dp[i] = OR over every word w that ends at position i: dp[i − len(w)]. Words are reusable → unbounded; answer yes/no → feasibility (OR). One string ≠ two-string pattern — the dictionary is the coin set, not a second string.
🕵️ "Burst balloons one by one; popping balloon i earns left·i·right. Maximize total." (LC 312)
Interval DP. The killer insight: think of the last balloon popped in [l, r] — its neighbours are then the fixed walls l and r, and the two sides become independent subranges. "Last action inside a range" = the interval signature. (Take/skip fails because popping changes neighbours — decisions aren't independent.)
🕵️ "Buy/sell stock any number of times, but after selling you must skip one day (cooldown)." (LC 309)
State machine. The cooldown is a rule about what you may do next → encode "what am I allowed to do" as a mode. Three circles, five arrows, done. (Greedy valley-peak works WITHOUT cooldown — the added rule is exactly what breaks it.)

🎤 How to ANSWER a DP Question in an Interview

  1. Restate + tiny example — "so for n = 3 the answer is 3, because…". Catches misunderstandings in 30 seconds.
  2. Say the brute force out loud — "naive recursion tries all choices, O(2ⁿ)". This is not wasted time; it IS the derivation.
  3. Spot the overlap — "the same (i, w) state repeats → I'll cache it". Name the state in plain English (Recipe ①).
  4. Code memoization first — it's fastest to get right under pressure.
  5. Offer upgrades — "I can convert to bottom-up and cut space to O(n)". Even just saying it scores.
  6. Dry-run a small case on the table before saying "done".

🚫 The 6 Classic DP Mistakes (Check Before Every Submit)

  • Base case off-by-one — verify dp's first real cell against a hand computation (remember dp[0]=1 in stairs!).
  • Wrong fill order — every cell you read must already be final. In 2-D: are you sure the row above is complete?
  • 1-D knapsack looping forward — items get cloned. 0/1 → loop capacity backwards.
  • Integer overflow — counting problems explode; use long or the required modulo (10⁹+7) from the start.
  • Answer in the wrong cell — "ending at i" states need max over all cells (LIS!).
  • State too small — if the transition needs information the state doesn't carry (LIS's "what does it end with?"), add it — a dimension or a redefinition.

🧠 Final Boss Quiz

You meet a brand-new DP problem in an interview. What is the correct FIRST move?
Derive, don't recall. Patterns speed you up, but the recipe is what works on problems you've never seen: tiny example → brute force → name the state → base → transition ("last move?") → answer location. That process is DP mastery — everything else in this course was practice for it. 🎓
n ≤ 18 and the problem says "visit every city exactly once, minimize cost". Which pattern?
Bitmask. The constraint n ≤ 18 is the loudest hint in competitive programming: 2¹⁸ = 262,144 subsets is fine, and "visited set" must live in the state → dp[mask][lastCity]. Constraints aren't decoration — they whisper the intended solution.
