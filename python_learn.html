Level 1 — Variables & Data Types

Names that point to objects — and why Python never asks you to declare a type

A variable is a name tag, not a box

In C/Java a variable is a box of fixed type. In Python it's a sticky label you can move to ANY object

  • x = 10 means: create an int object 10 somewhere in memory, then stick the label x on it.
  • x = "ten" later? Totally legal — the label just moves to a string object. This is dynamic typing.
  • The object has a type — the name never does. type(x) asks "what is x pointing at right now?"
  • Naming rules: letters, digits, underscore; can't start with a digit; case-sensitive (Age ≠ age); convention is snake_case.
🏷️
The one-line mental model"Assignment never copies data — it just makes a name point to an object." Remember this now; it explains lists behaving 'weirdly' later.

Level 2 — Control Flow

if / elif / else and the two loops — where programs start making decisions

🎬 Animation — if / elif / else picks ONE path

Rules that beginners break

  • The colon : ends every if / elif / else / for / while / def line. Forgetting it = SyntaxError.
  • Indentation is grammar. 4 spaces = "inside the block". Wrong indent = wrong program, not just ugly code.
  • elif chains are checked top to bottom — order matters! Put the strictest condition first.
  • Only ONE branch ever runs, then Python jumps below the whole chain.
  • = assigns, == compares. if x = 5: is a SyntaxError (Python protects you — C doesn't!).
shortcuts worth knowing 
# ternary — if/else in one line
status = "pass" if marks >= 40 else "fail"

# chained comparison — very Pythonic
if 0 <= marks <= 100:      # both checks at once
    print("valid")

# truthiness — empty things are False
if name:            # same as: if name != ""
    print("hello", name)

Scope — the LEGB rule

where does Python LOOK for a name? 
x = "global"

def outer():
    x = "enclosing"
    def inner():
        x = "local"
        print(x)   # local → found here first
    inner()

# search order: Local → Enclosing
#             → Global → Built-in  (LEGB)
⚠️
Assignment makes it localReading a global inside a function is fine. But assigning to it creates a NEW local unless you declare global x. Best practice: don't — pass values in, return values out.

The mutable default argument trap

the most famous Python interview bug 
def add_item(item, box=[]):    # ❌ DANGER
    box.append(item)
    return box

add_item(1)   # [1]
add_item(2)   # [1, 2] 😱 same list reused!

# defaults are created ONCE at def time.
# ✅ the fix:
def add_item(item, box=None):
    if box is None:
        box = []
    box.append(item)
    return box

Level 5 — Object-Oriented Python

Classes, self, inheritance and dunder methods — explained without jargon

Class = blueprint, object = the house built from it

One Dog class, many actual dogs — each with its own name in its own memory

  • __init__ is the constructor — it runs automatically every time you build an object, and its job is to fill in that object's data.
  • self = "THIS particular object". self.name means "the name belonging to the dog being handled right now". Python passes it automatically.
  • Attributes = the object's variables (self.name). Methods = the object's functions (speak).
  • Each object gets its OWN attributes: Dog("Rex") and Dog("Tomy") don't share names.
two dogs from one blueprint 
class Dog:
    def __init__(self, name, breed):
        self.name = name
        self.breed = breed
    def speak(self):
        return f"{self.name} says Woof!"

d1 = Dog("Rex", "Lab")     # __init__ runs
d2 = Dog("Tomy", "Pug")    # separate object
d1.speak()   # "Rex says Woof!"
d2.speak()   # "Tomy says Woof!"

Inheritance — reuse a whole class

child gets everything, overrides what it wants 
class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        return "..."

class Dog(Animal):            # Dog IS-A Animal
    def speak(self):          # override
        return "Woof!"

class Cat(Animal):
    def speak(self):
        return "Meow!"

for pet in [Dog("Rex"), Cat("Kitty")]:
    print(pet.name, pet.speak())
# Rex Woof! / Kitty Meow!   ← polymorphism:
# same call, each object answers its own way
🧬
super()calls the parent's version: super().__init__(name) inside the child's __init__ lets the parent do its setup first, then the child adds its own attributes.

Dunder methods — teach Python your type

__these__ hook into built-in syntax 
class Money:
    def __init__(self, rs):
        self.rs = rs
    def __str__(self):          # print(m)
        return f"₹{self.rs}"
    def __add__(self, other):   # m1 + m2
        return Money(self.rs + other.rs)
    def __eq__(self, other):    # m1 == m2
        return self.rs == other.rs

a, b = Money(50), Money(70)
print(a + b)       # ₹120 — + just works!

Comprehensions — a loop in one line

The same pattern works for lists, dicts and sets. Read it right-to-left: "for each x … keep if … transform to …"

list comprehension 
# the loop way
squares = []
for x in range(5):
    squares.append(x * x)

# the comprehension way
squares = [x * x for x in range(5)]
# [0, 1, 4, 9, 16]

# with a filter
evens = [x for x in range(10) if x % 2 == 0]
dict & set comprehension 
names = ["Ana", "Raj", "Zia"]

lengths = {n: len(n) for n in names}
# {'Ana': 3, 'Raj': 3, 'Zia': 3}

firsts = {n[0] for n in names}
# {'A', 'R', 'Z'} — a set

# transpose pairs
flip = {v: k for k, v in lengths.items()}
with map / filter flavor 
nums = [3, -1, 4, -5, 9]

# keep positives, square them
out = [n * n for n in nums if n > 0]

# same with map+filter (older style)
out = list(map(lambda n: n * n,
        filter(lambda n: n > 0, nums)))
# comprehension wins on readability!

Closures — functions that remember

the inner function keeps outer variables alive 
def make_counter():
    count = 0
    def step():
        nonlocal count
        count += 1
        return count
    return step

c1 = make_counter()
c1(); c1(); print(c1())   # 3
c2 = make_counter()
print(c2())               # 1 — own memory!
🧠
One line"A closure is an inner function that captures variables from its enclosing scope — they survive after the outer function returns." Decorators are built on closures.

💬 Rapid-fire Interview Q&A

Q1List vs tuple — when and why?+
List = mutable, for collections that grow/change. Tuple = immutable, for fixed records — safer, slightly faster, usable as dict keys and set members (hashable). If the data shouldn't change, a tuple documents that intent.
Q2What is the difference between == and is?+
== compares VALUES (calls __eq__). is compares IDENTITY — are both names pointing at the exact same object in memory? Two equal lists are == but not is. Only use is for None: if x is None.
Q3Shallow copy vs deep copy?+
a.copy() (shallow) copies the outer list but inner lists are still SHARED — changing a[0][0] also changes the copy's. copy.deepcopy(a) recursively copies everything. For flat lists shallow is enough; for nested structures you usually want deep.
Q4Why is a generator better than a list here?+
A list materializes ALL items in memory at once; a generator produces one item on demand and forgets it. For a 10 GB log file or an infinite stream, the generator uses constant memory. Trade-off: you can only iterate it once and can't index it.
Q5Explain decorators in one minute.+
A decorator is a function that takes a function and returns an enhanced replacement. @timer above def work() is just work = timer(work). Built on closures: the wrapper remembers the original. Used for logging, timing, caching (lru_cache), auth checks (Flask/Django).
Q6What is the GIL and why does it matter?+
The Global Interpreter Lock allows only one thread to run Python bytecode at a time, so threads don't speed up CPU-bound code. Threads still shine for I/O-bound work (network, disk waits). For true parallel CPU work, use multiprocessing — separate processes, separate GILs.
Q7How does Python manage memory?+
Reference counting: every object tracks how many names point to it; hitting zero frees it immediately. A cyclic garbage collector handles reference cycles (a→b→a). del x removes the NAME, not necessarily the object.
Q8What are *args and **kwargs actually?+
*args collects extra positional arguments into a TUPLE; **kwargs collects extra keyword arguments into a DICT. The names are convention — the stars do the work. Reversed at call sites: f(*mylist) unpacks a list into separate arguments.
